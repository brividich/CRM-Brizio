1. Come viene determinata la visibilità
Quattro livelli indipendenti: voce topbar, subnav, pulsante in pagina, route/pagina

Voce topbar

Il context processor legacy_nav() in core/context_processors.py (~287) costruisce nav_items e subnav_items usando due fonti in cascata:

1
Navigation Registry (prioritaria) — Query su NavigationItem + NavigationRoleAccess.
Se esiste almeno un record NavigationRoleAccess per la voce → filtra per ruolo.
Se nessun record → voce visibile a tutti fallback permissivo ⚠️
2
Fallback legacy — Pulsanti dalla tabella pulsanti + metadati UI
⚠️
Gate speciali via NAV_REGISTRY_ACL_GATES (context_processors.py ~24):
"tasks": "/tasks/" — la voce tasks usa check_permesso(legacy_user, "/tasks/") invece della sola visibilità ruolo.

Subnav

get_subnav_nodes(parent_code, role_id, is_admin) in core/navigation_registry.py (~132). Stessa regola del topbar: se nessun NavigationRoleAccess → visibile a tutti.

Pulsante in pagina

Due meccanismi separati e non collegati tra loro:

ModelloFileRigaEffetto
UserDashboardConfigcore/models.py~35visible per-utente per pulsante — solo template
UserModuleVisibilitycore/models.py~48visible per-utente per modulo — solo template
🚨
Questi flag nascondono il pulsante nel template ma non controllano l'accesso alla route. Un pulsante nascosto ha la route comunque accessibile via URL diretto.

Route / pagina

ACLMiddleware in core/middleware.py (~38) — su ogni request:

1
Bypass per path esenti (MIDDLEWARE_EXEMPT_PREFIXES)
2
Superuser Django → PASS
3
is_legacy_admin(legacy_user) → bypass totale → PASS
4
Altrimenti: check_permesso(legacy_user, path) → True o 403

Azione specifica

user_can_modulo_action(request, modulo, azione) in core/acl.py (~216). Non viene usata dal middleware — va chiamata esplicitamente nelle view quando serve.

3. Incoerenze rilevate
5 incoerenze strutturali tra i sistemi di visibilità e accesso
INC-A Visibilità menu ≠ accesso reale alla route
NavigationRoleAccess con regola "nessun record = visibile a tutti" crea un fallback permissivo.

Se una voce del Navigation Registry non ha record NavigationRoleAccess:
  • Il menu la mostra a tutti ✓
  • Ma il middleware ACL la gata via check_permesso() → un utente senza il pulsante corrispondente prende 403

Risultato: L'utente vede la voce nel menu ma cliccandola ottiene 403. I due sistemi non si parlano.
INC-B Pulsante nascosto ≠ route inaccessibile
UserDashboardConfig.visible=False nasconde il pulsante nel template ma non viene controllato dal middleware ACL. La route è raggiungibile direttamente via URL.
INC-C UserModuleVisibility disconnessa dall'ACL
UserModuleVisibility influenza solo la visibilità template, non l'accessibilità reale. Un modulo con visible=False per un utente è ancora navigabile se ha il permesso ACL.
INC-D Navigation Registry e ACL legacy non sincronizzati
Una voce NavigationItem può avere is_visible=True e is_enabled=True, ma se il Pulsante legacy corrispondente non esiste nella tabella pulsanti, check_permesso() non riesce a matchare il path → 403.

Non c'è nessun link esplicito tra NavigationItem.route_name e il pulsante legacy usato dall'ACL engine.
INC-E API gate separato dal pattern generale 
# core/middleware.py ~13
API_ACL_GATE_PATHS = {"/api/anomalie/": "/gestione-anomalie"}
Ogni nuova API deve essere aggiunta manualmente qui — facile dimenticarsi.

6. Bug potenziali
8 problemi identificati — alcuni con impatto diretto sulla sicurezza
BUG-1 Utente vede menu ma prende 403
Navigation Registry fallback permissivo + ACL via pulsanti legacy disgiunti.
Scenario: Voce NavigationItem senza NavigationRoleAccess → mostrata a tutti → click → check_permesso() fallisce perché pulsante legacy mancante → 403.
File: core/navigation_registry.py core/acl.py
BUG-2 Cache admin roles non invalida mai in-process ⚠️ 
# core/legacy_utils.py ~273
@lru_cache(maxsize=1)
def get_admin_role_ids() -> set[int]:
    return {int(r.id) for r in Ruolo.objects.filter(nome__iexact="admin")}
bump_legacy_cache_version() invalida Redis ma non questa cache Python in-process. Se si promuove un ruolo ad admin mentre il server è running → cambio non visibile fino al restart.
File: core/legacy_utils.py ~273
BUG-3 Fallback permissivo nel Navigation Registry
Voci senza NavigationRoleAccess → visibili a tutti.
Aggiungere una nuova voce al registry senza configurare i permessi la espone a tutti gli utenti immediatamente.

Regola attuale: opt-out (devi esplicitamente nasconderla)
Regola corretta: opt-in (devi esplicitamente darle visibilità)
File: core/navigation_registry.py
BUG-4 UserPermissionOverride.can_view=None semantica implicita
None = usa ruolo. False = nega sempre. Distinzione implicita nel codice, nessuna validazione a livello form/admin.
Un admin che setta can_view=None pensando di "revocare" l'override non fa nulla.
File: core/models.py ~15 core/acl.py ~89
BUG-5 API_ACL_GATE_PATHS richiede aggiornamento manuale
Ogni nuova API protetta con gate alternativo va aggiunta hardcoded nel middleware. Facile dimenticarsi.
File: core/middleware.py ~13
BUG-6 UserDashboardConfig.visible=False non è sicurezza
Nasconde il pulsante ma non blocca la route. Non è un bug di sicurezza (il middleware blocca comunque), ma crea falsa sensazione di controllo accessi. Può portare sviluppatori futuri a fidarsi della visibilità template come controllo sicurezza.
BUG-7 Due fonti di navigazione possono divergere
Se _navigation_registry_enabled() è True → usa registry. Se False → usa fallback legacy. Se le due fonti hanno dati diversi → l'utente vede menu diverso a seconda del flag, potenzialmente rivelando/nascondendo voci in modo inatteso.
BUG-8 consentito OR can_view nel permesso legacy ⚠️ 
# core/legacy_models.py ~103
view_allowed = bool(can_view) or bool(consentito)
Il campo consentito è residuo legacy. Se consentito=1 e can_view=0, l'accesso viene comunque concesso.
Un admin che setta can_view=0 pensando di bloccare l'accesso può essere sorpreso.
File: core/legacy_models.py ~103
